  ## Refuted or unverifiable claims

  ### N1 — HIGH: conflict guard rejects valid removals

  Spec:131–135 applies to every event. An open membership is precisely what a valid removal should close. After successfully migrating an add, the corresponding
  remove therefore becomes a conflict.

  Restrict and define the guard by action; removal validation must preserve balanced replay.

  Evidence: clients/index_membership_store.py:98–102,130–138; clients/pit_silver_revision.py:264–271.

  ### N2 — HIGH: recovery must precede conflict detection

  Spec:145–147 says an existing deterministic replacement completes rejection only. But spec:131–135 checks for an open verified membership first. A previously
  committed replacement add satisfies that condition.

  Explicitly detect a completed replacement before applying conflict checks. Reuse the stored replacement rather than reconstructing it with a new timestamp/
  revision.

  Evidence: clients/revisioned_parquet.py:56–60; clients/index_membership_store.py:116–119.

  ### N3 — HIGH: the duplicate-add check examines the wrong time range

  Spec:132 checks whether membership is already open at the incoming event’s effective time. A historical add can precede an existing nightly-sync add, so the
  guard passes even though replay subsequently encounters two adds.

  The check must validate the proposed event against the affected replay sequence, including later events. The operational ordering at spec:251–253 does not
  establish the claimed fail-closed fallback.

  Evidence: livewire_scripts/membership_sync.py:422–428; clients/pit_silver_revision.py:261–271.

  ### N4 — HIGH: fallback creates invalid delisted intervals

  Spec:190–194 sets missing-start candidates to:

  - effective_from = known_at
  - effective_to = delisted_utc

  For an already-delisted record, the end predates the fetch time. Candidate status does not relax interval validation, so append raises instead of recording the
  promised candidate.

  Specify a valid disposition for an unbounded historical record without inventing its start.

  Evidence: clients/security_master.py:197–202.

  ### N5 — MEDIUM: identity conflict policy remains inconsistent

  Spec:183 still resolves overlapping dates by closing the older interval at the newer start, without requiring compatible issuer evidence or adjudication of
  conflicting dates. Matching FIGIs do not override material contradictions.

  Spec:184 also labels differing-share-class conflicts candidate, whereas the contract distinguishes incomplete evidence from materially contradictory evidence.

  Evidence: docs/contracts/shepherd-security-identity.md:42–49,76–86; same-ID rows bypass collision checks at clients/security_master.py:174–175.

  ### N6 — MEDIUM: earliest-date skip can leave later intervals permanently uncovered

  Spec:97–99,116–117 skips fetching once the earliest membership date is covered. That does not establish coverage for later unresolved events. The newly
  specified widening rule cannot help if this skip prevents fetching.

  Check coverage of the unresolved dates needed by this pass, not only the earliest one.

  Evidence: clients/security_master.py:114–121; spec:186.

  ### N7 — MEDIUM: backlog cardinality changes silently

  Existing import/sync count distinct unresolved security IDs. Spec:165,227 changes this to rows. Three historical events for one unresolved ticker change the
  measurement from 1 to 3 without any deterioration.

  Preserve distinct-ID counting after active-row filtering, or explicitly distinguish the new event count so before/after acceptance remains comparable.

  Evidence: livewire_scripts/membership_sync.py:156,408,417; livewire_scripts/status.py:343–346.

  ### N8 — LOW: currency tie behavior is misstated

  Spec:204–205 says whichever row was appended last wins. The resolver updates only for strictly greater known_at. Equal timestamps retain the first row
  encountered—relevant when one fetch creates multiple identity rows.

  Correct the statement and include equal timestamps in the already-planned caller test. No interval-aware resolver redesign is requested.

  Evidence: livewire_scripts/sync_corporate_actions.py:688–693.

  3. Historical insertion before later add: store already contains resolved add at T2. Placeholder add has effective time T1, where T1 < T2. No membership is

     effective_to < effective_from and is rejected by the master.

  5. Later coverage skipped: existing verified interval covers T1 but ends before T2. Unresolved events need both dates. Earliest-date coverage skips the fetch;
     the T2 event remains unresolved on every retry.

  6. Currency tie: two verified rows for the same symbol share known_at and carry different currencies. Appending the second does not replace the resolver’s
     first selection.
