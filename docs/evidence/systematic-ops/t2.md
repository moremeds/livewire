## Source finding and decision

`release.promote()` atomically flips `current` then called `prune(keep)` destructively. The daily job's tail calls `housekeeping --apply`, which also called `prune(..., dry_run=False)`. The old pruner protected the new `current` target and newest releases, but could remove an older physical release still used by an in-flight job. Installed launchers for daily-update, intraday-catchup, membership-sync, coverage, digest and watchdog start from `current`; release-promote starts from the repo checkout. That read-only inspection establishes exposure, not the historical cause of the 2026-09-23 invalid `certifi` path. Its cause remains UNKNOWN.

The selected guard is deliberately conservative: promotion and housekeeping list release GC candidates without deleting them. Direct `prune()` defaults to preview. Destructive `prune()` requires `maintenance_window=True`, and the `release gc` CLI requires both `--apply` and `--maintenance-window`. The maintenance flag is an operator assertion, not a process detector. Before GC, new launchers must be paused and old-release jobs/children allowed to finish; a process snapshot without stopped launchers is subject to a launch-between-scan/delete race. During first rollout, old-code jobs must drain because their old housekeeping tail still has the destructive behavior. No new lease system or changes to installed launchers were made.

This deviates from the earlier idea of an automatic active-release lifetime guard because already-running old code cannot acquire a new lock, and updating all launchers would require a larger migration. Releases accumulate until reviewed maintenance GC, so internal disk usage must be inventoried before each cleanup decision (T14). Existing current/retention candidate selection is unchanged.
