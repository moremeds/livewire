# Livewire 数据完整性：后续方案与最终形态

状态：提案，供评审与后续执行。本文不授权生产数据替换、存储协议迁移或 Apex 改动。

## 1. 目标与完成标准

目标：损坏、写入中断、权限故障或数据源不可用再次发生时，系统能够保住
最后一份有效发布，准确指出受影响范围，并通过既定流程恢复，无须再写补丁。

“不再打地鼠”不意味着杜绝外部故障，而是同类故障不再演变成新代码需求。
最终验收必须同时证明：写入安全、发布一致、读取一致、故障可恢复、状态可信。
部署成功、进程退出 0、manifest revision 增加，均不能单独满足验收。

不引入新数据库、服务、队列或第二条数据写入路径。复用现有 Parquet、manifest、
lake lock、ledger、DuckDB、release 与测试基础设施；暂不建设通用事务框架。

## 3. 最终形态

```text
供应商数据
    │ 校验、规范化
    ▼
Bronze：按 symbol/timeframe 保存 canonical Parquet
    │ 临时文件完整验证 → 原子替换单个目标文件
    │ Silver 构建期间保护其所需输入，避免与写入交错
    ▼
Silver：不可变 daily/factor 文件 + 完整 manifest
    │ 唯一提交点：silver/revisions/current.json
    ├── Apex / PIT / 其他消费者：固定一个 manifest，按其路径读取
    └── DuckDB：由已提交数据派生的可重建目录

现有 ledger：记录运行、提交、失败范围和恢复结果
现有 status / digest：从上述事实给出可追溯结论
```

### 每一层只有一个明确职责

| 层 | 权威内容 | 必须保证 | 不保证的内容 |
|---|---|---|---|
| Bronze | 已接收的规范化原始记录 | 单文件写入完整；失败不覆盖有效旧文件 | 全市场所有 Bronze 文件同时切换版本 |
| Silver | 一个 manifest 命名的已提交派生数据 | 跨 symbol、daily/factor 的一次读取固定在同一发布 | 对外部盘损坏或断电的无条件持久性 |
| DuckDB | 可重建的查询目录与覆盖率统计 | 构建失败不覆盖旧目录；缺失范围可见 | 第二份 canonical bar 数据 |
| Ledger | 可追溯的运行与结果事实 | 能定位 run、lane、symbol、失败和恢复 | 替代数据文件或 manifest 成为数据真相 |
| Apex 等消费者 | 已接受的 snapshot | 一次逻辑读取及 reseed 不跨版本 | 通过固定路径回退偷偷补齐 manifest 缺项 |

一个 manifest 可以复用旧 generation 的未变化文件，并不要求每次复制全湖。
“同一 snapshot”指读取同一个 manifest 所选的文件集合，不要求它们来自同一目录。
部分 symbol 沿用旧数据时，必须保留实际日期并报告降级，不能借新 revision 冒充新鲜。

## 4. 分阶段执行

### P0：先修验收可信度

`depends_on: []`

- 复现 coverage 低于 95% 但进程成功的原因；统一数值精度和失败判定。
  用一个明确低于门槛的临时测试样例证明 CI 命令返回非零。
- 修复 quality_flags 的测试导入/mock 接缝，移除不再必要的 Linux 跳过；
  不降低阈值、不扩大 omit、不添加只为凑覆盖率的测试。
- 在 Linux CI 与 Mac mini 对应平台重新运行现有检查，保留实际百分比、skip 原因
  和退出码。门禁未通过时不得给新版本标记“可验收”。

主要文件：`pyproject.toml`、`.github/workflows/ci.yml`、
`tests/test_quality_flags.py` 及实际引发重复导入的测试接缝；按复现结果最小修改。

验收：低于门槛确实失败；支持平台的必需测试确实执行；精确合并 SHA 的全部门禁通过。

### P1：查清写入边界，防住损坏这一类问题

`depends_on: []`

- 保存 RJF 文件证据、时间戳、相关运行与发布记录，追踪所有可能写入其 canonical
  路径的调用链，包括计划任务、回填、修复和手工入口。读源码找所有 caller，
  不能只检查报错脚本。
- 核对每条路径是否复用已有 publisher；临时文件是否与目标位于可原子替换的
  同一文件系统；文件关闭、完整读取验证、同步与替换顺序是否正确。
- 运行时间线核对发现：coverage 自动 repair 与手工 rebuild-silver 不经过定时
  runner 的全局湖锁。必须把这些实际写入入口纳入同一协作边界，并避免父进程
  持锁后子进程重复取锁的死锁；不能仅以 daily/intraday 互斥判定安全。
- 对已证实的缺口在共同写入边界修复。只有发现重复实现才归并，避免另建一套
  “安全写入器”。已满足要求的路径只补必要证据，不重写。
- 在可丢弃的小数据集上复现截断、异常退出、进程被杀、权限拒绝和空间不足。
  首次写入失败不产生可用目标；更新失败不破坏原有效文件。
- 给实际发现的坏文件制定逐项恢复清单：来源、历史覆盖、替换前后校验和回退证据。
  执行替换需另行授权；保留原证据，不用删文件重下载掩盖根因。

验收：所有 canonical 写入入口有明确归属，同类故障测试通过。若无法重建历史
损坏原因，明确保留“原始原因未知”，不能把防护有效写成因果已证实。

### P2：完成 Silver 发布与消费者的一致性改造

`depends_on: [P0, P1, 存储与消费者改动批准]`

具体契约沿用 [Silver 原子发布设计](2026-09-08-silver-atomic-publication.md)，
本方案不另建第二套设计。核心要求如下：

1. 重建只写新的不可变 artifact；保留未变化文件的已提交路径与哈希。
2. 输入读取受现有锁或等效已验证机制保护。先核对所有写入者是否遵守同一边界；
   不以“最终 manifest 原子”掩盖构建时输入已混杂的问题。
3. 全部 artifact 校验通过后，以 `current.json` 替换作为唯一提交点。
4. Apex、DuckDB Silver 查询、PIT 和其他实际消费者固定一次 manifest，
   从中取文件路径；一个请求或 reseed 中途不得重新选择 current。
5. 中断留下的未提交文件永不自动成为 served 数据。重试新建 attempt；
   不靠刷新现有文件哈希或按“最新目录”收编残留物。
6. 单个 symbol 的质量问题只隔离该 symbol：旧数据仍通过完整性及语义校验才可
   沿用，并暴露真实新鲜度；否则从新 manifest 省略，消费者拒绝读取该项。
   首次发布没有有效旧数据可用时也遵循此规则。被选入 manifest 的 artifact
   校验失败、manifest 不完整或写入事务失败，才中止整次提交。
   完全无变化不产生新发布；局部隔离后即使提交成功，受影响范围仍不可标为健康。

Livewire writer 和 Apex reader 可按文件所有权并行开发，但必须一起集成验收。
遍历真实消费者后补齐范围；不能为了缩小 diff 留下固定路径旁路。

验收：真实子进程在各提交阶段被 SIGKILL 后，消费者只看到完整旧 snapshot 或
完整新 snapshot；已固定旧版本的读者不受新提交影响；重试无需人工清理即可完成。
另测并发 writer、无更新、损坏 artifact、manifest 缺项和历史 revision 读取。

### P3：让目录与状态描述同一份结果

`depends_on: [P2]`

- DuckDB 的 Silver 统计绑定到已提交 manifest；构建失败保留旧目录，同时显示
  当前构建失败和旧目录的实际时点，不把“仍能查”当作“已更新”。
- 完整性依据既有 preset、registry、资格/退市与交易日规则定义的预期集合。
  比较到 symbol/timeframe；`max(last_date)` 和视图非空只能作摘要。
- 在既有 ledger 中复用已有字段，列出真正缺失的信息后再决定是否需要协议扩展。
  状态应能区分执行完成、数据已提交、当前可用、数据新鲜和需要人工行动。
- 把残留失败按实际原因分类并指定下一步：合法无交易/退市、暂时供应商故障、
  数据不一致、文件损坏、未知。分类必须来自证据，不能为了变绿调标签。
- 有限自动重试只覆盖可安全重试的暂时错误；单个 symbol 的损坏/历史矛盾按 P2
  隔离并进入明确恢复流程，整体一致性失败则停止整次提交。恢复后用同一组验收
  条件关闭问题，不增加第二套恢复判断。

验收：一份报告能回答“哪个 run、哪个发布、哪些 symbol 未完成、为何、下一步是什么”；
失败数下降仍不能变成无故障。消费端接受的 revision 与报告引用的发布一致。

### P4：迁移、发布与真实运行闭环

`depends_on: [P0, P1, P2, P3, 生产切换批准]`

- 先用真实文件系统类型上的可丢弃数据验证同步、重命名与中断语义；
  进程崩溃验证不能冒充断电持久性验证。保留尚不能证实的硬件/文件系统限制。
- 清点部署版本、根路径、所有 writer/consumer 与实际存储余量。计算首次生成、
  重试残留和保留旧版本所需空间；不足则拒绝迁移，不临时删除历史版本腾空间。
- 切换窗口还须控制自动 release-promote、coverage repair 和手工写入入口。
  保护仍被旧进程使用的 release；当前默认 prune 只保护 current，不能替代该保证。
- 在批准的切换窗口暂停旧 Silver 写入，准备已验证的初始 snapshot；
  先部署支持 manifest 路径的消费者，再启用新 writer。逐个核对实际运行版本。
- 旧文件和旧 release 保留。新格式提交后不能直接切回旧 mutable writer；
  数据回退通过新递增 revision 引用旧的有效 artifacts，代码回退必须兼容格式。
- Claude 使用精确 released code 独立验收：故障注入、真实 manifest/文件哈希、
  Apex 读取与 watcher/reseed，再验证正常定时更新。还需覆盖一次无变化/重试路径；
  没有自然触发时在隔离数据集验证，不凭空要求连续几天“看起来没事”。

验收：每个项目的 commit、CI、release、进程、数据发布和消费结果分别有证据；
至少一次正常定时运行经过完整链路，未解决的数据质量问题逐项说明。

## 5. 依赖关系与交付方式

```text
P0 验收门禁 ───────────────┐
                          ├→ P2 原子发布与消费者 → P3 结果一致 → P4 切换与实跑
P1 写入边界与故障证据 ─────┘
```

P0 与 P1 可独立开展；P2 内部按 writer/reader 划分所有权。主负责人承担契约、
集成和最终验收，独立审核者负责破坏性场景与证据检查。每阶段交付 PR、对应
回归证据和剩余不确定性，不以提交数量或测试数量作为进度指标。

本次仅编写方案。涉及协议、Apex、生产切换和数据替换的批准是各自执行前置条件，
不影响先完成只读调查与可隔离的门禁修复准备。

## 6. 最终验收清单

- [ ] 低于覆盖率阈值的 CI 确实失败，必需测试不因接缝错误被跳过。
- [ ] canonical 写入入口全部有归属，同类损坏/中断不会破坏有效旧文件。
- [ ] Silver 唯一提交点成立，所有实际消费者按固定 manifest 读取。
- [ ] 中断与重试不依赖人工补哈希、收编孤儿或删除残留文件。
- [ ] catalog、ledger、status 与消费者指向同一份可解释的结果。
- [ ] 原有坏文件和 Silver 残留失败逐项恢复、解释，或明确保持阻塞。
- [ ] 精确 release 的真实定时运行和消费结果由 Claude 独立验证。
- [ ] 空间增长有测量与安全停止条件；尚未验证的断电持久性明确保留。

暂缓自动垃圾回收与后台自愈框架。只有不可变版本的真实增长量需要它们时，
再设计保留期、活动读者保护和可审计删除；不能在本轮顺带加入危险清理。

### 7.3 两个问题分别回答

**能否在任务运行时做迁移？**

- 可以并行开展源码开发、隔离测试和不读取活动湖的 artifact 构建。
- 对存储协议兼容的普通代码发布，已启动的任务固定在旧 release，后启动任务
  使用新 release；仍需保护旧进程使用的目录不被 prune。
- 当前 **不能批准无停写的 Silver 协议切换**。固定路径消费者、绕过湖锁的
  repair/手工 writer，以及初次 snapshot 的输入一致性都尚未闭合。
- 初次迁移需要经批准的停写窗口。先阻止新 writer 启动并等待已有 writer 完成，
  再持有一致性保护，完成初始 snapshot、消费者切换及核验。后台服务能否持续读
  旧 snapshot，取决于旧 snapshot 已验证且消费者已改造，不能预先承诺零停机。
- 今后不可变发布完成后，旧 snapshot 的读取与新版本构建可并存；这仍不意味着
  Bronze writer 可以任意改动正在构建所需的输入。

**新的 nightly 能否跑完？**

- 目前没有足够证据保证 13:00→18:00 内完成；既有 daily 已有超过五小时的样本，

- 1 秒与 60 秒的锁轮询只是获取倾向，不提供硬优先级、公平性或抢占。

  2340 秒记录是 declared 阈值，不是观测到的等待。

因此先测量，再确定时间表：分别测冷缓存的正常变更、无变化、首次完整迁移、
失败重试；记录总耗时、持锁时间、排队时间、写入量、校验时间和消费影响。
迁移预算必须独立于 nightly 增量预算，不能把一次性全量成本永久塞进 daily。

### 7.4 增加到方案的运行验收条件

1. **窗口目标明确**：用户尚未指定业务截止时间；暂以 daily 尽量在 18:00 前完成
   作为比较目标，不把它当作用户已批准的 SLA。
2. **所有写入都计入**：daily、intraday、coverage repair、手工重建/修复共同参与
   写入保护；旁路未闭合时，不允许迁移与现有写入并跑。
3. **切换以状态为准**：无活动 writer、无即将自动进入的 writer、锁已获取、
   活动 release 已保护、消费者准备完毕，才能开始。某个钟点或空进程列表不够。
4. **容量有可用证据**：需要完整成功的代表性样本与明确余量；超过目标时，先
   消除重复扫描/重复重建和非必要写入，再决定延后非关键工作，不直接增加并发。
5. **不靠时间猜依赖**：coverage 的最终结果针对已完成的目标数据评估；尚在写入
   的范围应为待完成，而不是立刻启动与主任务竞争的 repair。优先复用现有
   完成事实与锁，不新增调度服务。
